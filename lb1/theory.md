# 1. Подробный разбор кода (строка за строкой, по блокам)

Код разбит на логические части: генерация данных, эталон (классический) умножитель, функция выбора блока, блочное умножение, версии с `std::thread` и `std::async`, проверка корректности и `main`. Объясняю каждую часть подробно.

### Определения и типы

```cpp
using Matrix = std::vector<std::vector<double>>;
```

Матрица представлена как `vector` строк, каждая строка — `vector<double>`. Простой, удобный, но не самый быстрый контейнер из-за двойной индексации и возможной не-сплошной памяти.

---

### Генерация матрицы

```cpp
Matrix generateMatrix(size_t n, size_t m, int seed = 42) {
    std::mt19937 gen(seed);
    std::uniform_real_distribution<double> dist(0.0, 10.0);
    Matrix A(n, std::vector<double>(m));
    for (size_t i = 0; i < n; ++i)
        for (size_t j = 0; j < m; ++j)
            A[i][j] = dist(gen);
    return A;
}
```

* `std::mt19937` — детерминированный генератор псевдослучайных чисел (Mersenne Twister). `seed` позволяет получать повторяемые данные.
* Заполняем матрицу значениями в диапазоне `[0,10)`. Повторяемость важна для корректных замеров и дебага.

---

### Классическое (эталонное) умножение

```cpp
Matrix multiplyClassic(const Matrix& A, const Matrix& B) {
    size_t n = A.size(), m = B[0].size(), k = B.size();
    Matrix C(n, std::vector<double>(m, 0.0));
    for (size_t i = 0; i < n; ++i)
        for (size_t j = 0; j < m; ++j)
            for (size_t t = 0; t < k; ++t)
                C[i][j] += A[i][t] * B[t][j];
    return C;
}
```

* Тройной цикл `i, j, t` — базовый алгоритм перемножения матриц размерности `n x k` и `k x m`.
* Временная сложность `O(n*k*m)`. Для квадратных `n` это `O(n^3)`.
* Работает как эталон для проверки корректности параллельных версий.

---

### Автоматический выбор размера блока (tiling)

```cpp
size_t optimalBlockSize() {
    const size_t L1_CACHE_SIZE = 32 * 1024;
    size_t blockBytes = 3 * sizeof(double);
    size_t blockSize = static_cast<size_t>(std::sqrt(L1_CACHE_SIZE / blockBytes));
    return std::max<size_t>(8, blockSize);
}
```

* Идея: блоки матриц должны помещаться в небольшой кеш (L1). В блоковом умножении одновременно читаются элементы из блока A, блока B и пишется блок C. Учитываем 3 массива => `3 * sizeof(double)`.
* Берём квадратный блок размера `b x b`. Память под один «пакет» = `3 * b*b * sizeof(double)`. Приравниваем к L1 и решаем относительно `b`: `b ≈ sqrt(L1 / (3*sizeof(double)))`.
* Возвращаем минимум 8, чтобы не сделать блок слишком маленьким.
* Примечание: это приближение. На практике лучше экспериментировать и, возможно, учитывать L2/L3.

### Блочное перемножение для диапазона строк

```cpp
void blockMultiply(const Matrix& A, const Matrix& B, Matrix& C,
                   size_t blockSize, size_t rowStart, size_t rowEnd) {
    size_t n = A.size(), m = B[0].size(), k = B.size();
    for (size_t ii = rowStart; ii < rowEnd; ii += blockSize)
        for (size_t jj = 0; jj < m; jj += blockSize)
            for (size_t kk = 0; kk < k; kk += blockSize)
                for (size_t i = ii; i < std::min(ii + blockSize, rowEnd); ++i)
                    for (size_t j = jj; j < std::min(jj + blockSize, m); ++j)
                        for (size_t t = kk; t < std::min(kk + blockSize, k); ++t)
                            C[i][j] += A[i][t] * B[t][j];
}
```

* Это классическое «tiling» (blocking). Разбиваем все три измерения на блоки по `blockSize`.
* Внешняя петля `ii` проходит только по диапазону строк, который обрабатывает текущая нить (`rowStart..rowEnd`). Это позволяет безопасно распараллелить по строкам C: разные нити обновляют разные строки `C`.
* Внутри блока выполняется «локальное» умножение подблоков, что повышает локальность доступа к памяти и лучше использует кеш.
* Обратите внимание: `C[i][j]` суммируется через `+=` потому что разные kk дают частичный вклад в один и тот же `C[i][j]`.

### Версия с `std::thread`

```cpp
Matrix multiplyThreaded(const Matrix& A, const Matrix& B, size_t threads) {
    size_t n = A.size();
    Matrix C(n, std::vector<double>(B[0].size(), 0.0));
    size_t blockSize = optimalBlockSize();
    size_t rowsPerThread = (n + threads - 1) / threads;
    std::vector<std::thread> pool;
    for (size_t t = 0; t < threads; ++t) {
        size_t start = t * rowsPerThread;
        size_t end = std::min(start + rowsPerThread, n);
        if (start >= n) break;
        pool.emplace_back(blockMultiply, std::cref(A), std::cref(B), std::ref(C),
                          blockSize, start, end);
    }
    for (auto& th : pool) th.join();
    return C;
}
```

* Разбиваем строки матрицы C на равные диапазоны `rowsPerThread`. Каждая нить вызывает `blockMultiply` над своим набором строк.
* Используем `std::cref`/`std::ref` чтобы передать ссылки в `std::thread`.
* `join()` ждёт завершения нитей.
* **Почему это безопасно без мьютексов?** Потому что каждый поток изменяет разные строки `C`. Нет гонки при записи одних и тех же элементов. Чтение из A и B не требует защиты, если они const.

---

### Версия с `std::async`

```cpp
Matrix multiplyAsync(const Matrix& A, const Matrix& B, size_t threads) {
    // ... аналогично создаём C, blockSize, rowsPerThread ...
    std::vector<std::future<void>> futures;
    for (size_t t = 0; t < threads; ++t) {
        // вычисляем start,end
        futures.emplace_back(std::async(std::launch::async, blockMultiply,
                                        std::cref(A), std::cref(B), std::ref(C),
                                        blockSize, start, end));
    }
    for (auto& f : futures) f.get();
    return C;
}
```

* `std::async(std::launch::async, ...)` гарантирует создание отдельной задачи (и, как правило, отдельного потока).
* Поведение близко к `std::thread`, но управление задачами делегируется стандартной библиотеке.
* `future.get()` синхронизирует и выбрасывает исключения, если они были.

---

### Проверка корректности

```cpp
bool equal(const Matrix& A, const Matrix& B, double eps = 1e-6) { ... }
```

* Сравниваем поэлементно с допуском `eps`. Для чисел с плавающей точкой сравнение по абсолютной разности достаточно для однотипных входных данных. Для больших/малых значений можно использовать относительную ошибку.

---

### main: замер времени и вывод

* Создаём `A`, `B` размерами `n x n`.
* Замеряем время эталонной реализации, затем многопоточные версии.
* Выводим времена и проверку корректности.
* `threads = std::thread::hardware_concurrency()` даёт рекомендуемое число аппаратных потоков.

# 2. Теория: всё с нуля — от математики до практики оптимизаций

Я дам компактный, но полный набор понятий, которые нужны, чтобы понять, как и почему работает код и как его улучшать.

## 2.1 Что такое умножение матриц (в математике)

* Матрица `A` размера `n×k` и матрица `B` размера `k×m` дают матрицу `C` размера `n×m`.
* Элемент `C[i][j] = sum_{t=0..k-1} A[i][t] * B[t][j]`.
* Количество операций: для простого алгоритма `2 * n * m * k` FLOP (умножение + сложение). Для квадратных `n×n`: ≈ `2 n^3`.

## 2.2 Алгоритм тройного цикла

* Самый прямой алгоритм имеет три вложенных цикла.
* Порядки циклов (`i k j`, `i j k`, `k i j` и т.д.) влияют на локальность доступа к памяти и на производительность.
* На современных процессорах важно писать код, который использует кеш и векторные инструкции.

## 2.3 Почему кеш важен (память и производительность)

* Процессор читает память блоками (кеш-строками). L1 — самый быстрый, но маленький; L2/L3 — больше, но медленнее.
* Если данные, к которым вы обращаетесь в коротком промежутке, умещаются в кеше, то доступы быстрые.
* Блочное умножение увеличивает локальность: работаем с подблоками `b x b`, повторно используем данные из кеша, уменьшаем количество медленных обращений в ОЗУ.

## 2.4 Tiling / Blocking

* Разбиваем матрицы на блоки `b x b` и выполняем умножение блоков: это уменьшает пропускную способность памяти и увеличивает эффективность кеширования.
* Подбор `b` — критичен. Слишком малые блоки — лишний overhead; слишком большие — не помещаются в кеш.

## 2.5 Выбор размера блока

* Теоретическая формула для квадратного блока `b`: хотим чтобы `3 * b^2 * sizeof(element)` помещалось в выбранный кеш (обычно L1 или L2). Тогда `b ≈ sqrt(Cache / (3*elem_size))`.
* Практика: L1 ≈ 32KB, double = 8B → `b ≈ sqrt(32K / 24) ≈ 36`. Но реальные цифры зависят от ассоциативности кеша, конфликтов, дополнительных данных и кода.
* Эксперимент лучше теории: тестируйте несколько значений.

## 2.6 Параллелизм: как распараллелить умножение

* Разделяем работу по независимым кускам. Естественный выбор — по строкам матрицы C (каждая строка i вычисляется независимо).
* Нужно избежать гонок при записи в C. Если каждый поток пишет в разные строки/блоки — мьютексы не нужны.
* Распараллеливание по элементам/по столбцам возможно, но нужно аккуратно предотвратить false sharing.

## 2.7 False sharing

* Когда два потока записывают в разные переменные, но эти переменные лежат на одной кеш-строке, происходят лишние проталкивания кеша между ядрами. Это снижает скорость.
* Решение: выравнивание, паддинг, разделение работы по блокам, которые выровнены по кеш-линиям.

## 2.8 std::thread vs std::async

* `std::thread` даёт явный контроль над созданием и жизненным циклом потока.
* `std::async(launch::async, ...)` создаёт задачу; по стандарту обычно создаётся поток, но реализация и пул потоков зависят от платформы. `future.get()` синхронизирует и пробрасывает исключения.
* Для высокопроизводительных задач обычно используют явные потоки и собственный пул потоков (thread pool) для избежания лишних аллокаций и создания/уничтожения потоков.

## 2.9 Векторизация (SIMD)

* Современные компиляторы могут векторизовать внутренние циклы, исполняя несколько умножений одновременно (SSE, AVX, AVX2, AVX-512).
* `-march=native` позволяет компилятору генерировать SIMD-инструкции для вашей CPU. Но нужно писать код в форме, удобной для автoвекторизации (равномерные циклы, простые индексы).
* Для максимума используют библиотеки BLAS (OpenBLAS, Intel MKL) или явно пишут intrinsics.

## 2.10 Транспонирование B

* В классическом коде `B` читается по столбцам `B[t][j]`, что плохо для кеша, если строки `B` разнесены по памяти.
* Транспонирование `B` (храним `B_t[j][t] = B[t][j]`) позволяет читать по строкам и улучшить локальность. Часто даёт существенный прирост.

## 2.11 Параллельное планирование работы

* Статическое распределение по строкам (равно каждому `rowsPerThread`) простое и эффективно при равномерной нагрузке.
* Для неравномерной нагрузки лучше динамическая очередь задач, work-stealing или OpenMP `schedule(dynamic, chunk)`.

## 2.12 Измерение производительности (методика)

* Используйте `high_resolution_clock` или `steady_clock`.
* Делайте warm-up запуск, чтобы прогреть кеш и JIT/профилировку (если есть).
* Делаем несколько прогонов и усредняем.
* Измерять нужно wall-clock time, но контролировать частоту процессора и режим энергосбережения.
* Для отчётов считают GFLOPS: `GFLOPS = (2*n^3) / (time_seconds * 1e9)` для квадратных матриц.

## 2.13 Численные ошибки

* При операциях с плавающей точкой порядок сумм влияет на небольшой числовой шум. При сравнении результатов используйте относительную погрешность или `eps * max(1,|a|,|b|)`.

## 2.14 Память и представление матрицы

* `vector<vector<double>>` удобно, но данные не обязательно подряд в памяти. Лучше использовать одномерный массив `std::vector<double>` и индекс `i * stride + j`.
* Выровненная аллокация (`posix_memalign`, `aligned_alloc`) полезна для SIMD и для предотвращения перекрытия кеш-линий.

## 2.15 Продвинутые оптимизации и реальные решения

1. **Транспонируйте B** перед умножением.
2. **Используйте flat arrays** вместо `vector<vector<...>>`.
3. **Выравнивайте память** и применяйте `restrict`-подобные указания (в C++ нет `restrict`, но можно аккуратно организовать).
4. **Векторизация**: компилятор `-O3 -march=native` или ручные intrinsics.
5. **Пулирование потоков**: избегать частого создания/удаления потоков.
6. **Используйте BLAS** (OpenBLAS, MKL) для промышленной скорости.
7. **NUMA-aware** аллокация и привязка потоков (affinity) на больших серверах.
8. **Профилирование**: perf, VTune, likwid, чтобы найти узкие места.

## 2.16 Практические рекомендации для лабораторной работы

* Эксперименты: запускать при `n = 256, 512, 1024, 2048`. Маленькие `n` не дадут параллельного выигрыша.
* Менять `blockSize` в диапазоне 8..128 и строить график GFLOPS vs `blockSize`.
* Тестировать `threads = 1..2*hardware_threads`.
* Фиксировать частоту CPU или включать политку производительности (governor = performance).
* Собрать результаты в CSV и построить графики.

# Короткая сводка: почему ваш код заработает быстрее с этими улучшениями

1. **Генерация данных** даёт стабильные и детерминированные входы.
2. **Выбор блока** уменьшает обращения в медленную память и повышает кеш-локальность.
3. **Блочная обработка + распараллеливание по строкам C** убирает гонки и уменьшает коммуникации между потоками.
4. **std::async** и **std::thread** обеспечивают два способа управления задачами; их поведение похоже, но для больших задач лучше управлять потоками явно или использовать пул.
