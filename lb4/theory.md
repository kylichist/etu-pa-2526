# Полная теория по CUDA и GPU-программированию (на русском, формат Markdown)

Ниже — подробное, системное руководство по тому, что такое CUDA, как устроены GPU, какие инфраструктурные элементы входят в CUDA-стек и какие именно элементы были использованы в вашей реализации (matmul + сортировка с Thrust). Пишу с акцентом на то, чтобы ответ прошёл «очень тщательно» — включая понятия аппаратной архитектуры, модель выполнения, память, инструменты, библиотеки и типичные оптимизации.

---

## Краткое введение / цель

CUDA — это платформа и программная модель от NVIDIA для параллельных вычислений на GPU. Позволяет писать код, где часть работы исполняется на GPU (device), а управляющая часть — на CPU (host). CUDA особенно эффективна для задач, имеющих высокий уровень параллелизма (матричные операции, линейная алгебра, свёртки, сортировки и т.п.).

---

## Аппаратная основа: архитектура GPU (в терминах CUDA)

- GPU состоит из множества Streaming Multiprocessors (SM). Каждый SM — набор исполнительных блоков (ALU), регистров, кеш-памяти, и блоков для управления потоками.
- Warp — базовая единица планирования в CUDA: группа из 32 последовательных нитей (threads), которые выполняют одну и ту же инструкцию (SIMT — Single Instruction Multiple Threads).
- Каждый SM одновременно переключает выполнение между warps для скрытия задержек доступа к памяти.
- GPU имеет несколько уровней памяти:
  - Регистры (per-thread): самый быстрый, самый локальный.
  - Shared memory (on-chip per-block): быстрая память, доступная всем thread'ам блока (block). Часто используется для тайлинга (tiled algorithms).
  - L1 / L2 кеши: аппаратно-зависимы.
  - Global memory (device DRAM): большой объём, но высокая латентность; доступ через cudaMemcpy между host<>device.
  - Constant memory, Texture memory — специфичные области с кешированием, полезны для особых целей.
- Пиковая пропускная способность DRAM и производительность ALU — важнейшие аппаратные характеристики.

## Модель программирования CUDA (основные понятия)

- Host (CPU) и Device (GPU). Host вызывает kernel'ы, управляет памятью и синхронизацией.
- Kernel — функция, помеченная `__global__`, запускаемая на GPU. Пример:
  ```cpp
  __global__ void myKernel(float* A, int N) {
      int row = blockIdx.y * blockDim.y + threadIdx.y;
      int col = blockIdx.x * blockDim.x + threadIdx.x;
      // ...
  }
  ```
- Grid → блоки (blocks) → нити (threads). При запуске kernel'а вы указываете размеры сетки и блока: `kernel<<<gridDim, blockDim>>>(...)`.
- Каждый thread имеет идентификаторы `threadIdx`, `blockIdx`, `blockDim`, `gridDim`.

## Память и производительность (критично)

- Копирование данных между host и device происходит через `cudaMemcpy`. Эти копирования могут быть дорогими — их нужно минимизировать или выполнять асинхронно.
- Память может быть:
  - pageable host memory (обычная): копирование требует staging и занимает больше времени.
  - pinned (page-locked) host memory: `cudaHostAlloc` или `cudaMallocHost` — даёт более быструю H2D/D2H передачу и позволяет асинхронные memcpy со streams.
  - unified memory (`cudaMallocManaged`): единое виртуальное адресное пространство, упрощает программирование, но производительность и поведение миграции страниц нужно понимать.
- Коалезирование (coalescing): последовательные потоки должны обращаться к соседним адресам в глобальной памяти, чтобы получить высокую пропускную способность.
- Shared memory: используется для тайлинга и локальной коммуникации между потоками блока. Shared memory быстрее, но ограничена по объёму. Требует учёта bank conflicts.
- Bank conflicts: доступы потоков к разным "банкам" shared memory могут выполняться одновременно; конфликты снижают производительность.

## Синхронизация и согласованность

- `__syncthreads()` — синхронизация внутри блока (все thread'ы блока).
- Нет простой синхронизации между блоками внутри одного kernel'а — для глобальной синхронизации нужно завершить kernel и запустить новый.
- На host уровне: `cudaDeviceSynchronize()` ждёт завершения всех ранее запущенных операций в default stream.
- Атомарные операции: `atomicAdd`, `atomicCAS` и т.п. — для безопасного изменения общих переменных из разных потоков.

---

## Управление выполнением / Streams / Events

- Stream — последовательность операций (копирование H2D/D2H, kernel launches) выполняемых на устройстве. Разные streams могут выполняться параллельно, если устройство и драйвер поддерживают concurrency.
- Default stream (stream 0) блокирует другие streams (поведение зависит от настройок). Использование нескольких streams + асинхронных memcpy + pinned memory позволяет перекрывать вычисления и копирования.
- Events (`cudaEventCreate`, `cudaEventRecord`, `cudaEventElapsedTime`) — для точного тайминга GPU-операций (они измеряют время на устройстве, включая kernel и асинхронные memcpy, если записывать и синхронизировать события корректно).

---

## Компиляция / nvcc / PTX / Compute capability

- nvcc — CUDA compiler driver (часть CUDA Toolkit). Он:
  - Разделяет host (C/C++) и device (PTX/CUBIN) код.
  - Генерирует PTX (виртуальный ISA) или машинный код (SASS) для конкретной архитектуры (sm_xx).
- Compute capability (например 7.5, 8.6) — версия архитектуры GPU. Suffix `sm_86` указывает nvcc генерировать код для архитектуры 8.6 (Ampere GA10x). Для RTX 3050 Ti Laptop обычно рекомендуют sm_86 (проверьте точную compute capability вашей модели).
- Пример флагов:
  - `-gencode=arch=compute_86,code=sm_86` — сгенерировать код для SM 8.6.
  - `-lineinfo`, `-G` — для профайлинга / отладки (G резко снижает скорость).
- PTX может поставляться вместе с исполняемым файлом и JIT-компилироваться драйвером на целевой GPU, если бинарник не содержит кода для этой SM.

---

## CUDA Runtime API vs Driver API

- Driver API — низкоуровневый; Runtime API — удобная обёртка и используется чаще.
- В коде обычно применяют runtime API: `cudaMalloc`, `cudaMemcpy`, `cudaFree`, `cudaEvent...`.
- Driver API даёт больше контроля (например, управлять модулем PTX), но сложнее.

---

## Библиотеки CUDA (важные наборы)

- Thrust — C++ шаблонная библиотека высокого уровня (STL-подобна) для параллельных алгоритмов. Заголовочная библиотека, идёт вместе с CUDA Toolkit. Поддерживает `device_vector`, `sort`, `reduce`, `transform`, и т.д.
- cuBLAS — высокопроизводительная BLAS-реализация для CUDA (матрицы, вектора). Используется для линейной алгебры.
- cuFFT — быстрая библиотека FFT.
- cuRAND — генерация случайных чисел на GPU.
- cuDNN — оптимизированные нейросетевые примитивы (используется в DL).
- Набор этих библиотек часто даёт лучшую производительность, чем самописные ядра, и рекомендуется использовать их при возможности.

---

## Отладка и профилирование

- Nsight Compute — низкоуровневый профайлер ядра (анализ occupancy, memory throughput, warp execution, divergence).
- Nsight Systems — системный профайлер, показывает взаимодействие CPU<->GPU, streams, задержки.
- `nvprof` устарел; используйте Nsight.
- Для простых измерений kernel time — используйте CUDA events (они дают время на GPU, не затрагиваемое задержками host<>device при корректной записи).

## Основные приёмы оптимизации (практические)

- Тайлирование и использование shared memory (пример: tiled matrix multiplication) — уменьшает количество обращений к глобальной памяти.
- Минимизируйте количество host-device копирований; используйте pinned memory и асинхронные memcpy для перекрытия.
- Добейтесь coalesced accesses (последовательные потоки читают последовательные элементы).
- Учитывайте occupancy — достаточное число warps/SM, но не чрезмерно. Для оценки используется калькулятор occupancy или Nsight Compute.
- Уменьшайте divergence в ветвлениях внутри warp: избегайте if-ветвлений, которые приводят к разным путям выполнения в одном warp.
- Минимизируйте обращения к глобальной памяти и избегайте конфликтов в shared memory (банк conflicts).
- Используйте оптимизированные библиотеки (cuBLAS, Thrust, т.д.) где возможно.

## Что использовано в предоставлённом коде: подробное описание инфраструктурных элементов и API

Ниже перечислены конкретные элементы CUDA-стека и стандартной C++/Thrust-инфраструктуры, которые использованы в примере (main.cpp) и зачем они нужны.

1. nvcc
   - Роль: компилирует C++ + CUDA код, генерирует device-код (PTX/SASS) и вызывает системный компилятор (gcc/clang) для host-части.
   - Почему нужен: без nvcc нельзя корректно собрать kernel'ы `__global__` и использовать Thrust device-функции.

2. CUDA Runtime API (используемые функции)
   - cudaMalloc(void** ptr, size_t size)
     - Выделяет память на GPU (device global memory).
   - cudaFree(void* ptr)
     - Освобождает память на GPU.
   - cudaMemcpy(dst, src, size, cudaMemcpyHostToDevice / DeviceToHost)
     - Копирование между host и device (синхронное по умолчанию).
   - cudaEventCreate / cudaEventRecord / cudaEventSynchronize / cudaEventElapsedTime
     - Сервисные события для измерения времени операций на GPU.
     - Мы использовали их для точного замера времени H2D + kernel + D2H.
   - cudaGetLastError()
     - Возвращает код последней ошибки kernel'а; помогает отладке.
   - cudaDeviceSynchronize()
     - Синхронизация host с завершением всех операций device (часто применяется после thrust вызовов или для уверенного замера).

3. Ядро (kernel) и его элементы
   - `__global__ void matMulTiledKernel(...)` — tiled/shared-memory kernel для умножения матриц.
   - Использованы:
     - `__shared__ float As[TILE][TILE];` и `Bs` — shared memory для тайлов A и B.
     - `blockIdx`, `threadIdx`, `blockDim` — для расчёта индексов.
     - Внутри kernel — цикл по "тайлам" (numTiles), чтение данных в shared, `__syncthreads()` для синхронизации, затем внутренний цикл по `k` для умножения.
   - Зачем: tiled approach значительно уменьшает обращения в slow global memory и использует быстрый shared memory, что даёт существенное ускорение.

4. Host-реализация (CPU) для сравнения
   - Простая naive-реализация матричного умножения (тройной цикл) — для baseline (лр1).
   - CPU QuickSort — рекурсивная реализация для сравнения со GPU-сортировкой.

5. Thrust
   - `#include <thrust/device_vector.h>`
   - `#include <thrust/sort.h>`
   - `thrust::device_vector<int> dvec = a;` (копирование host->device)
   - `thrust::sort(dvec.begin(), dvec.end());`
   - `thrust::copy(dvec.begin(), dvec.end(), a.begin());` (device->host)
   - Что такое Thrust: header-only, идёт вместе с CUDA Toolkit; предоставляет высокоуровневые контейнеры и алгоритмы, работает через backend CUDA. Используется для реализации GPU-сортировки (эффективно и безопасно).

6. Замер времени (в коде)
   - CPU: `std::chrono::high_resolution_clock` (host-side timing) — меряет wall-clock на CPU для функции matMulCPU и quicksort_cpu.
   - GPU: cudaEvent-based timing — записывали start до H2D memcpy и stop после D2H memcpy; затем `cudaEventElapsedTime` даёт время в миллисекундах.
   - Важно: такой замер GPU включает время на memcpy (H2D/D2H) + kernel execution. Это даёт end-to-end время, полезно для реальной оценки, но если нужен только чистый kernel time — событие нужно записывать непосредственно до/после вызова kernel и учитывать только это.

7. Проверки корректности и обработка ошибок
   - `CUDA_CHECK` макро — проверяет возвращаемые коды функции CUDA и печатает подробности в случае ошибки.
   - Проверка результата: после D2H сравнивается `C_gpu` и `C_cpu` максимальной разницей (maxdiff), чтобы убедиться в корректности.

8. Компиляция / флаги (рекомендации в коде/в комментариях)
   - Пример компиляции: `nvcc main.cpp -O3 -std=c++14 -o lab4_cuda`
   - Для оптимизации под вашу карту: `-gencode=arch=compute_86,code=sm_86` (для compute capability 8.6, типично для RTX 3050 Ti Laptop).
   - Для отладки: `-G` и `-lineinfo`.

## Почему использовал Thrust для сортировки, а не hand-made GPU-QuickSort

- Реализация эффективного параллельного QuickSort на GPU — нетривиальная задача (параллельный partition, управление стэком/очередями задач, балансировка нагрузки). Существуют реализации, но они сложнее и требуют детальной настройки.
- Thrust предоставляет высокопроизводительную, хорошо протестированную реализацию сортировки (использует radix sort / merge sort под капотом в зависимости от данных и типа). Для задач лабораторной работы сравнение CPU QuickSort vs Thrust::sort даёт корректную демонстрацию GPU ускорения.
- Если преподаватель требует конкретно QuickSort на GPU — можно реализовать, но это существенно увеличит объём работы.

## Практические советы при развёртывании в WSL / Windows

- На Windows нужно установить NVIDIA драйвер с поддержкой WSL (специальный драйвер/совместимость). Затем в WSL можно установить CUDA Toolkit (как пакет в Ubuntu внутри WSL).
- В WSL после установки драйвера и toolkit проверьте `nvidia-smi` и `nvcc --version`.
- Thrust идёт в составе CUDA Toolkit — дополнительные установки не нужны.

## Профилирование и раздельный анализ затрат времени

- End-to-end измерения (H2D + kernel + D2H) полезны для оценки реального ускорения при обмене данными.
- Для оптимизации полезно измерять отдельно:
  - H2D time (host->device)
  - kernel time (cuda events вокруг kernel)
  - D2H time
- Используйте `cudaEventRecord(start); kernel<<<>>>(); cudaEventRecord(stop);` и извлеките `elapsedTime` — это даст kernel-only время.
- Для CPU — замерять только вычислительную часть, исключая аллокации/генерацию данных, если хотите честное сравнение.

## Типичные ошибки и «подводные камни»

- Сравнивать CPU naive implementation с GPU optimized kernel неправильно без учёта возможности ускорить CPU (BLAS, multi-threading). Для честного сравнения указывайте, что именно сравниваете (single-threaded naive CPU vs GPU).
- Забывать учитывать время копирования H2D/D2H — особенно критично при маленьких задачах, где копирование «съедает» выигрыш от GPU.
- Не учитывать occupancy / регистровые ограничения, которые могут уменьшить эффективность kernel.
- Использовать `-G` в релизной сборке (сильно тормозит).
- Не проверять ошибки CUDA API (cudaGetLastError) — ошибки kernel'а могут быть «тихими».
- Неправильно выбирать `blockDim`/`gridDim` — плохой выбор ведёт к низкой загрузке GPU.
