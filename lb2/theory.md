# Theory

## 1. Что такое потокобезопасность

**Потокобезопасность** — это свойство программы или структуры данных, когда несколько потоков (threads) могут работать с ней **одновременно**, без нарушения данных или логики.

* **Поток (thread)** — это «мини-программа», которая выполняется параллельно с другими.
* Если два потока одновременно изменяют одну переменную или структуру данных, могут возникнуть **гонки данных (data races)**.
* Пример: два потока добавляют элемент в очередь без синхронизации → очередь может «сломаться» (например, потерять элемент или повредить память).

---

## 2. Проблема обычных структур данных

Стандартные структуры (например, `std::queue`, `std::list`) **не потокобезопасны**, потому что они рассчитаны на один поток.

Если их использовать одновременно из нескольких потоков без защиты, то:

* могут переписываться указатели,
* теряться данные,
* программа может крашиться.

---

## 3. Способы сделать структуру потокобезопасной

Есть несколько подходов:

### 3.1 Грубая блокировка (coarse-grained lock)

* Берётся **один мьютекс (mutex)** на всю структуру.
* Каждый поток перед операцией `push` или `pop` блокирует мьютекс, делает операцию, затем разблокирует.
* Просто, безопасно, но **неэффективно**:

  * Даже если несколько потоков только читают данные, они ждут друг друга.
  * Поток, который делает маленькую операцию, блокирует всех.

Пример:

```cpp
std::mutex mtx;
std::queue<int> q;

void push(int x) {
    std::lock_guard<std::mutex> lock(mtx);
    q.push(x);
}

bool pop(int &x) {
    std::lock_guard<std::mutex> lock(mtx);
    if (q.empty()) return false;
    x = q.front();
    q.pop();
    return true;
}
```

---

### 3.2 Тонкая блокировка (fine-grained lock)

* Вместо одного мьютекса берётся несколько.
* Например, для связного списка можно блокировать только **узел**, который меняется.
* Эффект: **лучше параллельность**, но код сложнее.

---

### 3.3 Без блокировок (lock-free)

* Используются **атомарные операции** (`std::atomic`) вместо мьютексов.
* Поток может изменить структуру, не блокируя других.
* Преимущество: высокая производительность при больших нагрузках.
* Недостаток: очень сложная реализация, особенно **освобождение памяти** (см. ниже).

Пример: lock-free очередь (MPMC — multiple producer, multiple consumer).

---

## 4. Проблема освобождения памяти (hazard pointers, epoch-based reclamation)

В lock-free структурах нельзя просто делать `delete` элементов, потому что другой поток может их ещё читать.
Поэтому применяются специальные техники:

1. **Hazard pointers** – поток «говорит», что сейчас читает элемент → никто не может удалить его.
2. **Epoch-based reclamation** – память удаляется только после того, как все потоки «завершили эпоху», когда элемент мог быть видим.

---

## 5. Метрики производительности

Чтобы измерить скорость работы структуры, обычно смотрят:

| Метрика            | Что показывает                                                                            |
| ------------------ | ----------------------------------------------------------------------------------------- |
| throughput (ops/s) | Количество операций в секунду                                                             |
| avg_ns             | Среднее время операции                                                                    |
| p50/p90/p95/p99    | Перцентили — показывают, что **95% операций выполняются быстрее p95**, а 1% медленнее p99 |

---

## 6. Как тестируют потокобезопасные структуры

1. Создают несколько потоков **читателей** и **писателей**.
2. Измеряют:

   * разные соотношения читателей/писателей (например, 1:1, 4:1, 1:4),
   * разное количество потоков (2, 4, 8, 16…).
3. Сравнивают:

   * lock-free,
   * тонкая блокировка,
   * грубая блокировка.
4. Строят графики: **производительность vs количество потоков**.

---

## 7. Проблема твоего теста

То, что ты запускал сейчас:

```txt
lockfree,65536,1,1,2,10,0,9240578,919321.784,524.079,515,537,546,580
lockfree,65536,1,1,2,10,0,170277621,17027586.581,78.516,79,83,84,91
```

* Это **всего одна конфигурация потоков** → на графике будет **одна точка**.
* Чтобы получить график, нужны **несколько измерений**:

  * разные количества потоков,
  * разные соотношения писателей/читателей,
  * разные размеры очереди.

---

## 8. Что делать на практике

1. Написать цикл тестов:

```cpp
for (int threads : {1,2,4,8,16}) {
    for (int readers = 1; readers <= threads; ++readers) {
        int writers = threads - readers;
        run_test(readers, writers, queue_size);
    }
}
```

2. Сохранять все результаты в CSV.
3. Потом строить графики:

```python
import pandas as pd
import matplotlib.pyplot as plt

df = pd.read_csv("results.csv")
for t in df['threads'].unique():
    subset = df[df['threads'] == t]
    plt.plot(subset['readers'], subset['throughput_ops_per_sec'], label=f"{t} threads")
plt.xlabel("Readers")
plt.ylabel("Throughput ops/sec")
plt.legend()
plt.show()
```
