### 1. Методика эксперимента (вставлять графики не нужно)
Описание методики и измерений.

1.1. Обозначения и параметры тестов
- producers — число потоков–производителей (P).  
- consumers — число потоков–потребителей (C).  
- per — число элементов, публикуемых каждым производителем.  
- capacity — ёмкость ограниченной очереди (для очередей).  
- total_ops = producers * per.  
- elapsed_s — полное wall‑clock время прогона (секунды).  
- throughput_ops_s = total_ops / elapsed_s (операций в секунду).  
- latency: по каждому извлечению потребителем вычислялась задержка в наносекундах как now_ns() (время потребления) − sent_ts (временная метка, записанная продюсером), затем значения приведены в CSV в микросекундах (mean_us, p50_us, p90_us, p99_us, p999_us, max_us).  

1.2. Метод измерений (пошагово)
- В продюсере перед помещением значения в очередь формировалась временная метка sent_ts = now_ns() (nanoseconds).  
- В консьюмере при получении элемента вычислялась задержка now_ns() − sent_ts; задержки аккумулировались в локальные векторы для каждого консьюмера.  
- Для неблокирующих реализаций (lock‑free) в нагрузочных режимах использовался цикл `try_push` / `try_pop` с коротким `yield` (busy‑wait) до успешной операции; для MutexQueue в части тестов использовались блокирующие push/pop.  
- Для списков в перформанс‑тестах основной сценарий удаления реализован как pop_front/try_pop_front (O(1)) для исключения квадратичного поведения удаления по значению при больших объёмах данных.  
- После завершения прогона локальные данные склеивались и вычислялись агрегированные метрики; строки результатов сохранялись в `perf_results.csv` в формате, указанном в файле.

### 2. Описание реализованных модулей и ключевых функций (согласно main.cpp)
(Вставлять графики не нужно; раздел описывает кодовую базу, на которой выполнены измерения.)

2.1. MutexQueue<T> (ограниченная кольцевая очередь, coarse‑grained)
- Поля: буфер std::vector<T> buf; head, tail, cnt; std::mutex m; std::condition_variable cv_not_full, cv_not_empty.  
- API:
  - try_push(const T&): неблокирующая попытка положить элемент; возвращает false, если очередь полна. При успешной записи вызывает cv_not_empty.notify_one().  
  - try_pop(T&): неблокирующая попытка достать элемент; возвращает false, если очередь пуста. При успешном извлечении вызывает cv_not_full.notify_one().  
  - push(const T&): блокирующая запись; ждет cv_not_full до появления места.  
  - pop(T&): блокирующее извлечение; ждет cv_not_empty до появления элемента.  

2.2. LockFreeMPMCQueue<T> (bounded lock‑free MPMC)
- Структура Slot: std::atomic<size_t> seq; T data.  
- Поля: уникальный массив Slot[] длины capacity; std::atomic<size_t> enqueue_pos, dequeue_pos; std::mutex wait_mtx; std::condition_variable cv_not_full, cv_not_empty (для блокирующих обёрток).  
- API:
  - try_push(const T&): читает enqueue_pos, проверяет slot.seq == pos; CAS enqueue_pos -> pos+1; записывает data; slot.seq.store(pos+1, release); notify_one cv_not_empty; возвращает true при успехе, false если полный.  
  - try_pop(T&): симметрично для dequeue_pos; при успешном чтении slot.seq.store(pos + capacity, release); notify_one cv_not_full; возвращает true/false.  
  - push/pop (блокирующие): реализованы через wait_mtx + condition_variable, в предикате вызывают try_push/try_pop повторно (ядро операций остаётся lock‑free; блокировка только для ожидания).  

2.3. MutexList<T> (однонаправленный список с глобальной блокировкой)
- Поля: Node* head; std::mutex m.  
- API:
  - insert(const T&): new Node, вставка в head под защитой m.  
  - remove(const T&): поиск первого совпадения и удаление под защитой m (линейная сложность).  
  - try_pop_front/pop_front: удаление и возвращение головы под общей блокировкой (pop_front в перформанс‑тестах).  
  - find, snapshot, clear: вспомогательные методы.  

2.4. FineGrainedList<T> (hand‑over‑hand locking)
- Поля: Node* head; std::mutex head_m; каждый Node содержит std::mutex m.  
- API:
  - insert(const T&): добавление в head под head_m (короткая блокировка для обновления указателя головы).  
  - remove(const T&): hand‑over‑hand (lock coupling) — по ходу обхода захватываются mutex‑ы node->m; при удалении обновляется prev->next или head под head_m и выполняется delete узла; реализация обеспечивает корректный порядок захватов/разблокировок для избежания дедлока.  
  - try_pop_front/pop_front: удаление головы под head_m (O(1)). Реализовано специально для перформанс‑тестов, чтобы избежать линейных обходов при массовом удалении.  

2.5. Модуль замеров и CSV‑вывода
- Собранные метрики записываются в `perf_results.csv` с колонками: impl, phase, producers, consumers, per, capacity, total_ops, elapsed_s, throughput_ops_s, samples, mean_us, p50_us, p90_us, p99_us, p999_us, max_us.  
- Формат значений: mean_us и перцентильные значения в CSV представлены в микросекундах.

### 5. Анализ полученных данных (факты, без оценочных суждений)
На основании содержимого `perf_results.csv` приводятся фактологические наблюдения.

5.1. Сравнение LockFreeQueue и MutexQueue (выдержки)
- Для конфигурации 4p×4c (per=200000, capacity=65536) LockFreeQueue фиксируется со средним временем 4.5 µs и throughput ≈ 3.65×10^6 ops/s; для MutexQueue в тех же условиях средняя латентность составляет 9,480.5 µs и throughput ≈ 2.08×10^6 ops/s (данные приведены в CSV).  
- В других конфигурациях (1p×1c, 1p×4c и т.д.) CSV содержит конкретные величины mean_us, p50_us, p90_us, p99_us и max_us для каждой реализации; значения можно сверить по таблицам в разделе 4.1–4.3.

5.2. Зависимость от числа производителей и потребителей (фактические цифры)
- При росте числа производителей при consumers=1 (см. таблицу 4.2) наблюдаются изменяющиеся throughput и mean_us у обеих реализаций; таблица 4.2 содержит конкретные значения для P=2,4,8.

5.3. Влияние ёмкости очереди (фактические наблюдения)
- Для LockFreeQueue при capacity = 1024/4096/16384 зафиксированы средние латентности 88.1/60.3/41.9 µs соответственно (см. таблицу 4.3). В том же эксперименте при capacity=65536 зафиксирован mean_us=11,668.5 µs. Аналогично для MutexQueue задокументированы значения mean_us для указанных capacity. Все эти значения представлены в CSV.

5.4. Поведение реализаций списков при insert + pop_front (факты)
- Для сценария insert + pop_front, producers=4, per=200000, обе реализации списка (MutexList и FineGrainedList) имеют mean_us порядка 0.8–0.9 µs и throughput порядка 4.0×10^6 ops/s (см. таблицу 4.4). Соответствующие строки находятся в `perf_results.csv`.
